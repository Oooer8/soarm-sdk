SOARM SDK Documentation

A practical reference for setting up, calibrating, controlling, visualizing, and debugging a SOARM / SO-ARM101 style robotic arm with Feetech STS3215 servos.

Install

Install the package in editable mode from the repository root.

pip install -e .

This workspace uses the soarm-sdk conda environment for local validation.

conda run -n soarm-sdk python -m pip install -e .
conda run -n soarm-sdk soarm-sdk status --config configs/soarm-sdk.yaml --mock
Mock mode is useful for CLI, Web, and documentation checks. It does not replace real checks for wiring, servo IDs, voltage, torque behavior, or mechanical range.

Hardware

The current target is a SOARM / SO-ARM101 style arm using Feetech STS3215 servos at 1 Mbps. The SDK talks to the bus through soarm_sdk.hardware.ServoBus, backed by scservo_sdk.

Servo IDs must already match the YAML configuration. The SDK does not infer joint order from the bus. If several new servos share the factory default ID, connect and rename one servo at a time with vendor or low-level Feetech tooling.

shoulder_pan1Base yaw
shoulder_lift2Shoulder pitch

Configuration

configs/soarm-sdk.yaml is the shared entry point for CLI, Web, and Python API usage.

includes:
  runtime: runtime.yaml
  motor_profile: motors/feetech_sts3215.yaml

configs/soarm-sdk.yaml

Arm name, serial port, baud rate, joint IDs, calibration, soft limits, and named poses.

configs/runtime.yaml

Control frequency, feedback frequency, Web sync/render rates, voltage threshold, and max step.

configs/motors/feetech_sts3215.yaml

Feetech register policy: PID, return delay, acceleration, mode, and gripper protection.

Joint limits

max_vel_rad_s and max_acc_rad_s2 are joint-space safety and planning limits, not direct per-move Feetech register values.

First Bring-Up

  1. Inspect wiring, power, linkage travel, and gripper clearance with power off.
  2. Assign servo IDs to match configs/soarm-sdk.yaml.
  3. Install the SDK and run the mock status command.
  4. Scan and save the serial port.
  5. Run real status and inspect communication, voltage, raw position, and soft-limit results.
  6. If calibration is missing or stale, run calibration.
  7. Save calibration and immediately run post-calibration status.
  8. Check the Feetech motor profile.
  9. Try a small low-speed move or named pose.
  10. Open the Web GUI for visual feedback and slider control.
conda run -n soarm-sdk soarm-sdk ports --config configs/soarm-sdk.yaml
conda run -n soarm-sdk soarm-sdk status --config configs/soarm-sdk.yaml
conda run -n soarm-sdk soarm-sdk calibrate --config configs/soarm-sdk.yaml --output configs/soarm-sdk.yaml
conda run -n soarm-sdk soarm-sdk configure-motors --config configs/soarm-sdk.yaml --check-only
conda run -n soarm-sdk soarm-sdk home --config configs/soarm-sdk.yaml --duration 2.0

Web GUI

Start the local browser console:

conda run -n soarm-sdk soarm-sdk web --config configs/soarm-sdk.yaml --mock

Without --mock, the Web server talks to the configured serial bus. The default URL is http://127.0.0.1:8765/.

PhasePurpose
DetectSelect port, save arm name/port, edit runtime frequencies, and run status.
CalibrateDisable torque, capture zero, sweep all joints, review new limits, and save calibration.
Visualize/controlLoad URDF, stream real joint feedback, enable torque, and send slider targets through SDK safety checks.
The Web GUI only enters control when a calibration exists, current status passes, and current joint positions are inside saved soft limits.

Teaching Record And Replay

Record joint-space demonstrations as JSON:

soarm-sdk record-demo demos/pick_place.json --config configs/soarm-sdk.yaml --duration 10 --hz 20
soarm-sdk record-demo demos/elbow_only.json --config configs/soarm-sdk.yaml --joints shoulder_pan elbow_flex

Validate and replay safely:

soarm-sdk replay-demo demos/pick_place.json --config configs/soarm-sdk.yaml --dry-run
soarm-sdk replay-demo demos/pick_place.json --config configs/soarm-sdk.yaml --speed 0.5
soarm-sdk replay-demo demos/pick_place.json --config configs/soarm-sdk.yaml --output-hz 200 --interpolation pchip

The demonstration format is soarm_sdk.demonstration.v1. It stores created_at, metadata, selected joints, and time-stamped radian samples. Replay validates the file, moves through a safety-checked lead-in, interpolates sparse samples to setpoints, and reuses SDK limit checks.

Python API

from soarm_sdk import SOARM

with SOARM.from_config("configs/soarm-sdk.yaml") as arm:
    arm.enable()
    arm.move_home(duration=1.5)
    arm.move_joints(
        {
            "shoulder_pan": 0.0,
            "shoulder_lift": -0.4,
            "elbow_flex": 0.8,
        },
        duration=2.0,
    )
    print(arm.get_joint_positions())

Online streaming

from soarm_sdk import SOARM

with SOARM.from_config("configs/soarm-sdk.yaml") as arm:
    stream = arm.start_joint_stream(output_hz=200, target_timeout_s=0.15)
    try:
        stream.update_target({
            "shoulder_pan": 0.0,
            "shoulder_lift": -0.35,
            "elbow_flex": 0.65,
        })
        print(stream.snapshot())
    finally:
        stream.stop()

stream_joints() remains a one-shot setpoint write for simple caller-driven streams. start_joint_stream() is the long-lived online controller for teleoperation, with latest-target overwrite semantics, fixed-rate output, velocity/acceleration limiting, and timeout hold behavior.

Demonstration helpers

from soarm_sdk import SOARM, record_demonstration, replay_demonstration

with SOARM.from_config("configs/soarm-sdk.yaml") as arm:

    replay_demonstration(arm, "demos/pick_place.json", speed=1.0)

Safety Gates

Use status as the read-only gate before real motion. It checks:

  • configured servo IDs are online
  • current positions can be read
  • current positions are inside soft limits
  • voltage is above the configured threshold

Calibration readiness is different from control readiness. Old soft limits may fail while communication, voltage, and raw position reads are still healthy enough to recalibrate. Control requires a saved calibration and a passing current status.

LayerDefaultPurpose
Trajectory input30 HzHigh-level targets from policy, user input, or planner.
Controller output200 HzConvert online stream targets or timed trajectories into regular setpoints.
Feedback sampling100 HzRead and cache real joint state.
Web state sync30 HzSend cached state to the browser.
Web rendering60 HzUpdate the visualization.

Troubleshooting

SymptomLikely causeNext step
Status fails on communication Wrong serial port, baud rate, cabling, power, or servo ID. Run soarm-sdk ports --config configs/soarm-sdk.yaml --no-update, then verify wiring and IDs.
Status fails only on soft limits The arm is outside saved limits or calibration is stale. Move the arm back into range and rerun status, or recalibrate.
Goal_Position changes but servo does not move Torque, operating mode, motor profile, current/load, or command block issue. Run probe-joint and inspect Torque_Enable, Operating_Mode, Moving, Acceleration, and Goal_Velocity.
Replay lead-in reports a large remaining delta The joint is not following position commands or present-position readback is stale. Probe the failing joint and slow lead-in with --lead-in-duration.
Voltage fails Power supply is below threshold or unstable. Do not move until power is corrected, then rerun status.
Joint direction or zero looks wrong Bad zero capture, direction inference, or sweep range. Stop motion, recalibrate, and verify zero ticks and radian limits before enabling torque.

Architecture

CLI and Web are thin adapters. Shared SDK layers own configuration, hardware rules, calibration math, safety, kinematics, teaching replay, and config writes.

Applicationssoarm_sdk.cli, soarm_sdk.web, soarm_sdk.webapp, examples, scripts
Application helperssoarm_sdk.application builds Web/CLI payloads and workflow state.
Teachingsoarm_sdk.demonstration owns demonstration JSON data, validation, recording, and replay.
SDK facadesoarm_sdk.arm.SOARM exposes the user-facing Python API.
Robot domaindiagnostics, calibration, kinematics, motion, and safety
Motion and safetymotion and safety own point-to-point moves, one-shot setpoints, online streams, timed replay, and safety checks.
Hardware bussoarm_sdk.hardware owns register I/O, units, torque, modes, PID, and motor profile writes.
Data and configsoarm_sdk.model and soarm_sdk.config define dataclasses, YAML schema, and split-config persistence.
Keep high-level planning out of ServoBus. Motion planning, retargeting, and safety policy should stay in the motion and SDK layers.
  • ServoBus caches sync readers and writes the Feetech seven-byte position command block that starts at Acceleration.
  • SafetyGuard and safety.limits centralize soft-limit, step, voltage, velocity, acceleration, and minimum-duration checks.
  • JointStreamingController writes only when its output reference advances; reached or stale targets hold without redundant bus writes.
  • SOARMConfig.save() preserves split config files when saving back to configs/soarm-sdk.yaml.
  • soarm_sdk.motor_profile and soarm_sdk.workflows are compatibility re-export modules; new internal code should use hardware.motor_profile and application.workflows.

Development And Validation

Use mock checks before touching hardware:

PYTHONPYCACHEPREFIX=/private/tmp/soarm-sdk-pycache conda run -n soarm-sdk python -m compileall src tests
conda run -n soarm-sdk python -m unittest discover -s tests -v
conda run -n soarm-sdk soarm-sdk status --config configs/soarm-sdk.yaml --mock
conda run -n soarm-sdk soarm-sdk fk --config configs/soarm-sdk.yaml shoulder_lift=-0.3 elbow_flex=0.5
conda run -n soarm-sdk soarm-sdk ik --config configs/soarm-sdk.yaml 0.42 0.0 0.20
conda run -n soarm-sdk soarm-sdk record-demo /tmp/soarm-demo.json --config configs/soarm-sdk.yaml --mock --duration 1
conda run -n soarm-sdk soarm-sdk replay-demo /tmp/soarm-demo.json --config configs/soarm-sdk.yaml --dry-run

Focused unit tests cover online streaming behavior. Compile checks and mock CLI paths remain the lightweight regression baseline for broader SDK flows.

When changing code, keep these boundaries intact:

  • ServoBus owns register I/O only.
  • SOARM exposes the public SDK facade.
  • Motion planning and safety live outside the hardware bus layer.
  • CLI and Web call shared workflow/API code instead of duplicating calibration math, safety gates, FK/IK, or config writes.
